# M1 backend — implementation plan

Spec: `PLAN.md` (decisions and Milestone 1). Branch `m1-backend`.

**Goal:** a daily GitHub Actions job that reads the shared calendar, has an AI label the events that block a trip, finds free windows, prices them with SerpApi Explore under the 230-a-month cap, stores every price, and sends instant deal alerts plus a Sunday summary to both phones through ntfy.

**Global constraints**
- Python 3.11+. Dependencies: `icalendar`, `recurring-ical-events` (RRULE expansion), `pyyaml`, `tzdata`. HTTP uses stdlib `urllib` and storage uses stdlib `sqlite3`. Tests: `pytest`.
- Every time is in America/Chicago.
- No web server in M1, and no secrets in git (`config.yaml` is git-ignored).
- Pure logic (windows, picking, scoring, alert rules) lives apart from I/O so tests need no network.

**Layout**
```
backend/pyproject.toml, config.example.yaml
backend/flybye/windows.py   pure: holidays(), candidates(), is_free()
backend/flybye/cal.py       fetch iCal → Event list (recurring expanded)
backend/flybye/db.py        sqlite schema + helpers
backend/flybye/ai.py        blocker labels (Gemini; provider list), cached, overrides
backend/flybye/serp.py      SerpApi explore/flights calls → price rows; search counter
backend/flybye/pick.py      pure: allowance, choose windows, baseline, score, alert rules, message text
backend/flybye/__main__.py  CLI: daily | windows | summary | test-notify; ntfy
backend/tests/
deploy/create-lxc.sh, update.sh, flybye.service, flybye.timer, SETUP.md
```

**Interfaces**
- `Event(uid, title, start: datetime, end: datetime, all_day: bool, free: bool)` comes from cal.py. ai.py and windows.py use it.
- `Window(kind, out: date, ret: date, holiday: str|None)`. `.id` = `f"{kind}:{out}:{ret}"`. windows.py produces it, and serp.py and pick.py use it.
- Price row dict: `window_id, kind, out, ret, code, name, price, hotel, minutes, airline, stops, source`. serp.py produces it, db.py stores it, pick.py reads it.

## Task 1: windows
- `holidays(year) -> dict[date, str]`: New Year, MLK, Presidents, Memorial, Juneteenth, July 4, Labor, Thanksgiving + the Friday after, Christmas.
- `candidates(today, cfg) -> list[Window]`:
  - **weekend**: Fri→Sun, out within 2–10 weeks.
  - **3day**: Thu→Sun and Fri→Mon, 2–12 weeks.
  - **long**: Sat start, each length in `nights` (default [7]), 3–17 weeks.
  - Each type has a config on/off switch and its own week range.
  - `holiday` holds the name of any holiday from out to ret.
- `is_free(window, blockers, cfg)`: the trip occupies [out at `depart_hour` − 3h, ret at 21:00 + 3h]. `depart_hour` is 17 for Thu/Fri departures and 7 for Saturdays. Any blocker event overlapping that span blocks the window.
- Tests: weekend lead-time edges; Fri→Mon gets the Labor Day tag; a blocker on Fri at 15:00 blocks a Fri departure (inside the 3h buffer); one on Fri at 13:00 doesn't; an all-day event on Sat blocks; a turned-off type gives no windows.
- Run `pytest tests/test_windows.py`. Expected: all pass.

## Task 2: calendar
- `parse(ics_text, start, end) -> list[Event]` expands recurring events with `recurring_ical_events`. A `date` start is an all-day event running from 00:00 to the end date at 00:00. `free` = TRANSP is TRANSPARENT.
- `fetch(url)` uses urllib.
- Tests: a fixture with one weekly RRULE, one all-day event, and one event in UTC; check how they expand and convert to Chicago time.

## Task 3: db + AI labels
- db tables:
  - `labels(key PK, title, block INT, why, src, at)`
  - `prices(... row fields ..., seen)`
  - `searches(at, engine, window_id)`
  - `alerts(at, code, out, ret, price, kind)`
  - `meta(k PK, v)`
- `label_events(events, db, cfg, chat=http_chat) -> dict[key, bool]`:
  - key = `uid|title`.
  - A config override wins, matched case-insensitively on the title or by uid.
  - If the key is cached, use the cache.
  - Otherwise, batch unlabeled events (40 per call) into a prompt asking for a JSON array `[{"i":n,"block":bool,"why":str}]`.
  - Providers are tried in order. If all fail, the events block and nothing is cached.
- Tests use a fake `chat`: caching (a second run makes no call), overrides, fallback to the next provider, "everything failed blocks", and JSON wrapped in prose or code fences.

## Task 4: serp + pick
- serp.py:
  - `explore(window, area, cfg)` and `flights(window, city_or_code, stops, cfg)` → rows. Each logs one row to `searches`.
  - The window kind sets the parameters: `adults`, `stops` (from config), `travel_mode=1`.
  - `confirm(row, cfg)` → (`lowest_price`, `typical_low`, `typical_high`, first-leg times).
- `pick.allowance(cap, used_this_month, today)` = (cap − used) // days left in the month, including today, with a minimum of 0.
- `pick.cost(window, cfg)`: 1 for weekend/3day. Long trips cost `len(long.areas)`, plus 1 for each wish city with its own `stops` that allows long trips.
- `pick.choose(windows, last_searched: dict, allowance, cfg)`: windows never searched come first, then the oldest searched, with the nearest `out` breaking ties. Add windows while their cost fits the allowance.
- `pick.baseline(rows_for_code_kind)`: the median, needing ≥4 rows from ≥2 windows, else None.
- `pick.deal_candidates(new_rows, baselines, cfg)`: wish-city rows that are ≤ `deal_ratio` (0.8) of the baseline, or have no baseline yet. Sorted by ratio, capped at `confirm_per_run` (2).
- `pick.should_alert(row, confirm, sent_alerts, today, cfg)`: price ≤ `typical_low`; fewer than `max_instant_per_week` (2) instant alerts this ISO week; and no earlier alert for the same (code, out, ret) unless the price is ≤ 0.9 × what we sent.
- `pick.score(row, baseline, window, cfg)`: % under the baseline, minus `hour_penalty` × hours, plus `wish_bonus`, plus `holiday_bonus`.
- `pick.summary(...)`: top 3 wish-list picks plus the best non-wish-list pick, each latest price row for a window that's still free; followed by the event labels made since the last summary.
- `pick.fmt_row(...)` formats a pick as: city · Fri Nov 13–Sun Nov 15 · $410 for 2 (23% under usual) · 2h56 nonstop · hotel ~$150.
- Tests cover all of the pure functions.

## Task 5: CLI
- `python -m flybye daily`:
  1. Calendar → labels → free windows.
  2. allowance → choose → search → store.
  3. Candidates → confirm → alerts → notify.
  4. On Sunday, also send the summary.
- `windows` prints the free windows and the labels. It makes no SerpApi calls.
- `summary` sends the summary now.
- `test-notify` sends a test message.
- Notifications go out as a POST to `{ha.url}/api/services/notify/<service>` for each target.
- Check: `daily` runs end to end against a temporary database. Run it with the real config once the secrets exist; until then `windows` runs with a fixture ics.

## Task 6: GitHub Actions
- `.github/workflows/daily.yml`: cron `0 13 * * *` (08:00 Chicago in winter; 07:00 in summer), plus `workflow_dispatch`. It sets up Python 3.12, installs `backend`, runs `python -m flybye daily` with the secrets as environment variables, then commits `data/flybye.db` when it changed (`contents: write`).
- `SETUP.md`: create the private repo, add the 4 secrets, install ntfy on both phones and subscribe to the topic, then run the workflow by hand once.
